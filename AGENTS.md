# AGENTS.md — Verde Marea: контекст проекта и правила работы с ИИ

Это единственный файл инструкций для ИИ-агентов (`CLAUDE.md` содержит только ссылку на него). Он описывает контекст и порядок работы, а не готовые решения: код и шаблоны ИИ пишет под конкретную задачу, ответственность за результат остаётся на человеке.

## Что это за продукт

Система бронирования столов ресторана Verde Marea с локальным запуском: интерфейс, серверная логика, PostgreSQL, упрощённая авторизация, роли, правила бронирования, административный контур, история изменений. Самостоятельный продукт, не переделанная референс-сборка.

**Роли.** `user` (гость): выбирает дату, время и число гостей, видит только доступные окна, бронирует, отменяет до дедлайна. `admin`: ведёт поток броней, меняет статусы, управляет окнами записи, видит назначенный стол и историю броней. `super_admin`: всё, что `admin`, плюс смена ролей `user` ↔ `admin` и полная история (роли, регистрации). Роль `super_admin` задаётся только через seed.

**Стек.** Next.js, React, TypeScript, Tailwind CSS, Zod, PostgreSQL, Prisma 7, bcryptjs, vitest, npm.

**Правила бронирования.** Окна считаются по правилам, а не хранятся списком: 14 дней вперёд (сегодня и 13 дней), вторник–воскресенье, шаг 90 минут, старты 12:00–21:00, без прошедшего времени, без закрытых админом окон, только при наличии подходящего свободного стола. Стол подбирается по наименьшей достаточной вместимости и сохраняется в брони; администратор может пересадить гостей вручную. Статусы: `pending` → `confirmed` | `cancelled`; `confirmed` → `cancelled` | `completed` | `no_show` (последние два только после начала брони); конечные статусы не возвращаются. Самостоятельная отмена гостем — не позднее чем за 3 часа до начала. Стол нельзя назначить двум активным броням на пересекающееся окно; у пользователя не может быть двух активных броней на одно время (проверяется в сервисе и ограничениями БД).

**Безопасность.** Пароли только как `passwordHash` от `bcryptjs.hash(password, 12)`, проверка `bcryptjs.compare(...)`; `passwordHash` никогда не попадает в UI и API-ответы. Роли и все ограничения проверяются на сервере. Сессия: cookie `vm_session`, в БД хранится хеш токена.

## Порядок работы над задачей

1. **Сформулировать результат:** что должно быть наблюдаемо после выполнения (например, «гость не видит окно, если нет стола на 6»).
2. **Назвать слой и этап** из `Plan.md`. Не смешивать слои в одной задаче без причины.
3. **Перечислить правила**, которых касается задача, со ссылкой на раздел `SPEC.md`.
4. **Перечислить негативные случаи** до реализации: что должно быть отклонено и каким ответом.
5. **Небольшими шагами:** один шаг — одна проверяемая вещь.
6. **Проверить самому:** запустить, прочитать вывод, а не полагаться на «должно работать».
7. **Записать** результат в `CHECKS.md` и обновить `Plan.md`, если этап сдвинулся.
8. **Если нашёл баг:** исправить и повторно проверить функции, которые исправление могло задеть (см. «Что перепроверять» ниже).

## Что ИИ делает, а что решает человек

- ИИ: предлагает варианты с компромиссами, пишет и проверяет код, находит расхождения со спецификацией, указывает риски.
- Человек: утверждает допущения (`SPEC.md`), границы MVP, всё, что необратимо (удаление данных, сброс БД, пуш в репозиторий).

## Красные линии

- Проверки прав, дедлайна и пересечений — только на сервере; клиентские проверки лишь для удобства.
- Пароли: только `bcryptjs`, 12 раундов; никаких других схем и никакого логирования паролей.
- `passwordHash` не покидает серверный слой.
- Не добавлять внешние интеграции, деплой и продакшен-инфраструктуру.
- Не хранить секреты в репозитории: в git только `.env.example`, настоящий `.env` в `.gitignore`.
- Не менять схему БД без миграции; применённые миграции не редактировать.
- Не копировать сгенерированные каркасы поверх существующих файлов без проверки конфликтов.
- Время хранится как `timestamptz`; клиент Prisma создаётся только через `createPrismaClient` (`src/lib/db.ts`), он закрепляет сессию в UTC: драйвер читает и пишет `timestamptz` по поясу соединения, иначе время сдвигается на разницу с поясом сервера PostgreSQL. Не создавайте `PrismaClient` напрямую.
- Не добавлять корневой `loading.tsx`: он превращает серверные редиректы защищённых страниц в ответ 200 с meta refresh вместо настоящего 307 (ловит `npm run smoke`).
- Права проверяются в нескольких слоях намеренно (маршрут и сервис); источник правил один: `permissions.ts`.
- Интеграционные тесты очищают таблицы: `TEST_DATABASE_URL` обязан указывать на локальную базу с «test» в имени и отличаться от `DATABASE_URL` (проверяет `tests/support/safe-db.ts`).

## Что перепроверять после исправления

| Исправили | Проверить заново |
|---|---|
| расчёт доступности окон | создание брони, назначение стола, защита от дублей, список броней в админке |
| роли и права | гость, `admin`, `super_admin`, смену ролей, историю изменений |
| статусы и машину состояний | админские переходы, отмену гостем и дедлайн, уведомления, историю |
| схему БД | миграции с нуля, seed, ограничения БД, все тесты |
| стили и компоненты | гостевые и админские экраны, мобильную ширину, контраст |

## Команды

`npm run db:setup` (миграции + клиент + seed), `npm run db:seed`, `npm run db:reset` (сброс БД; в агентной сессии нужно явное согласие пользователя), `npm run dev`, `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`, `npm run smoke` (сквозная проверка на запущенном сервере).

## Критерий «готово»

Поведение подтверждено запуском, негативные случаи проверены, нет расхождений со `SPEC.md` и `design.md`, запись в `CHECKS.md` есть, связанные функции перепроверены.

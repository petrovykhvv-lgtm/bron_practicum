# Спецификация Verde Marea (Этап 1)

Статус: утверждено (допущения с пометкой **[предложение]** приняты).

## 1. Легенда

Verde Marea — небольшой ресторан средиземноморской кухни у воды. Тон бренда: спокойный, тёплый, неторопливый; морская зелень, золото и тёплый кремовый фон. Гость хочет быстро занять стол без звонков, ресторан хочет видеть поток заявок и не терять контроль над залом.

Продукт — самостоятельная система бронирования для одного ресторана, запускается локально.

Зал **[предложение]**: 8 столов — 3 на 2 персоны, 3 на 4 персоны, 1 на 6 персон, 1 на 8 персон. Максимум гостей в одной брони — 8.

## 2. Граница MVP

**Входит**
- Регистрация, вход, сессия, проверка ролей на сервере.
- Выбор даты, времени и числа гостей; расчёт доступных окон по правилам.
- Создание брони (`pending`), автоназначение стола.
- Личный кабинет: свои брони, отмена до дедлайна, внутренние уведомления.
- Админ-контур: список броней с фильтрами (статус, дата), смена статусов, управление окнами записи, просмотр назначенного стола.
- Управление ролями (`super_admin`).
- История изменений (`AuditLog`).
- Локальный запуск: PostgreSQL, Prisma, миграции, `seed`, `reset`.

**Не входит**
- Внешние интеграции (email, SMS, платежи, карты, мессенджеры).
- Публичный деплой, CI/CD, мониторинг и прочий продакшен-контур.
- Редактирование схемы зала через UI, лист ожидания, повторяющиеся брони, отзывы.

## 3. Роли

| Роль | Суть |
|---|---|
| `user` | Гость: бронирует и отменяет только свои брони. |
| `admin` | Персонал: ведёт брони, окна записи и пользователей в пределах своей роли. Не управляет `super_admin`. |
| `super_admin` | Всё, что `admin`, плюс повышение до `admin` и понижение обратно. |

## 4. Матрица прав

| Действие | Аноним | `user` | `admin` | `super_admin` |
|---|---|---|---|---|
| Регистрация, вход | да | — | — | — |
| Смотреть доступные окна | да | да | да | да |
| Создать бронь | нет | да (себе) | да (себе) | да (себе) |
| Видеть свои брони и уведомления | нет | да | да | да |
| Отменить свою бронь (за ≥3 ч) | нет | да | да | да |
| Видеть все брони, фильтровать | нет | нет | да | да |
| Подтвердить / отменить / завершить / `no_show` | нет | нет | да | да |
| Управлять окнами записи | нет | нет | да | да |
| Видеть список пользователей | нет | нет | да (без `passwordHash`) | да |
| Менять роли `user` ↔ `admin` | нет | нет | нет | да |
| Менять роль `super_admin` | нет | нет | нет | нет **[предложение]**: роль `super_admin` задаётся только seed |
| Смотреть историю изменений | нет | нет | да (брони и окна записи) | да (всё, включая роли и регистрации) |

Правило: каждая проверка выполняется в серверном слое; скрытая кнопка в UI защитой не считается.

## 5. Сценарии

**Пользовательские**
1. Регистрируется, входит, получает сессию.
2. Выбирает дату, время, число гостей; видит только допустимые окна.
3. Создаёт бронь → `pending`, стол назначен автоматически.
4. Открывает «Мои брони» и уведомления.
5. Отменяет бронь не позднее чем за 3 часа до начала; после дедлайна отмена отклоняется сервером.

**Административные**
1. Открывает админ-контур, фильтрует брони по статусу и дате.
2. Подтверждает или отменяет заявку, завершает визит, отмечает `no_show`.
3. Видит назначенный стол и историю действий по брони.
4. Управляет окнами записи.

**Служебные**
1. Запуск: миграции, `seed` (роли, столы, тестовые пользователи, примеры броней).
2. `reset`: пересоздание БД с нуля.
3. `super_admin` меняет роль пользователя; в `AuditLog` попадает запись «кто, кого, с какой роли на какую».
4. Любая смена статуса брони создаёт запись в `AuditLog` и уведомление владельцу брони.

## 6. Правила бронирования

**Доступные окна** вычисляются, не хранятся списком:
- ближайшие 14 дней;
- вторник–воскресенье (понедельник выходной);
- старты каждые 90 минут, 12:00–21:00 → 12:00, 13:30, 15:00, 16:30, 18:00, 19:30, 21:00;
- прошедшее время исключается;
- окно скрыто, если нет стола подходящей вместимости, свободного на этот интервал;
- окна, закрытые администратором, исключаются.

**Допущения [предложение]**
- Бронь занимает ровно одно окно (90 минут).
- Подходящий стол — свободный стол минимальной достаточной вместимости.
- Активные брони — `pending` и `confirmed`.
- Время ресторана — единая локальная таймзона, задаётся в `.env`.

**Инварианты (проверяются на сервере и в БД)**
- Стол не назначается двум активным броням на пересекающийся интервал.
- Пользователь не имеет двух активных броней на одно время.
- Назначенный стол сохраняется в брони.

**Машина состояний [предложение]**

| Из | В | Кто |
|---|---|---|
| `pending` | `confirmed` | admin, super_admin |
| `pending` | `cancelled` | владелец (до дедлайна), admin, super_admin |
| `confirmed` | `cancelled` | владелец (до дедлайна), admin, super_admin |
| `confirmed` | `completed` | admin, super_admin |
| `confirmed` | `no_show` | admin, super_admin |

`cancelled`, `completed`, `no_show` — конечные. Недопустимый переход возвращает ошибку и ничего не меняет.

## 7. Модель данных

Схема: [prisma/schema.prisma](prisma/schema.prisma). Миграции: `init` (таблицы) и `booking_constraints` (правила на уровне БД). Время хранится в UTC, дни недели и время окон считаются по `RESTAURANT_TZ` (по умолчанию `Europe/Moscow`).

| Сущность | Поля (главное) | Зачем |
|---|---|---|
| `User` | email (уникальный), name, `passwordHash`, role, даты | гость, `admin`, `super_admin` |
| `Session` | `tokenHash` (уникальный), userId, expiresAt | сессия; токен в cookie, в БД только хеш |
| `Table` | name (уникальное), capacity, isActive | зал; столы не удаляются, а деактивируются |
| `Slot` | startsAt (уникальный), isClosed, reason, updatedById | явное управление окном: администратор закрывает или снова открывает окно |
| `Booking` | userId, tableId, startsAt, endsAt, partySize, status, comment | бронь хранит назначенный стол |
| `Notification` | userId, bookingId, type, title, body, readAt | внутренние уведомления гостя |
| `AuditLog` | actorId, action, entityType, entityId, before/after (JSON), createdAt | история действий |

**Как `Slot` работает вместе с правилами.** Окна не хранятся списком: их порождают правила (раздел 6). `Slot` — только запись об изменении администратором: строка с `isClosed = true` скрывает окно из выдачи, `isClosed = false` возвращает его. Нет строки — окно управляется только правилами.

**Что можно восстановить из схемы**
- *Гость:* регистрация (`User`, `Session`) → выбор окна (правила + `Slot` + `Booking` + `Table`) → бронь (`Booking`, `Notification`, `AuditLog`) → «Мои брони» (`Booking` по `userId`) и уведомления (`Notification`) → отмена (`Booking.status`, дедлайн из `startsAt`).
- *Администратор:* список броней с фильтрами (`status`, `startsAt`), смена статуса (`Booking`, `AuditLog`, `Notification`), закрытие окон (`Slot`), назначенный стол (`Booking.tableId`), история (`AuditLog` по `entityId`).
- *Служебное:* смена роли (`User.role` + `AuditLog.user_role_changed` + `Notification.role_changed`), восстановление картины действий по `AuditLog.actorId`.

**Действия в `AuditLog`:** `user_registered`, `user_role_changed`, `booking_created`, `booking_status_changed`, `slot_closed`, `slot_reopened`.

### Правила и где они гарантируются

| Правило | Код | БД |
|---|---|---|
| Окна: 14 дней (сегодня и 13 вперёд), вторник–воскресенье, шаг 90 минут, старты 12:00…21:00, без прошедшего | `candidateWindows` | — |
| Окно скрыто, если закрыто админом или нет свободного подходящего стола | `availableWindows` | — |
| Подбор стола: активный, `capacity ≥ гостей`, свободен; из подходящих берётся наименьший по вместимости | `pickTable` | триггер `booking_table_fit` (вместимость и активность стола) |
| Гостей от 1 до 8 | `availableWindows` | `CHECK booking_party_size_range` |
| Один стол — одной активной брони на пересекающийся интервал | проверка до записи | `EXCLUDE booking_table_no_overlap` |
| У пользователя одна активная бронь на пересекающееся время | `userHasConflict` | `EXCLUDE booking_user_no_overlap` |
| Дедлайн самостоятельной отмены: не позднее чем за 3 часа до начала | `canOwnerCancel` | — |
| Переходы статусов и роли | `checkTransition` | — |
| Смена ролей: только `super_admin`, только `user` ↔ `admin`, `super_admin` не меняется | `checkRoleChange` | — |
| `passwordHash` не выдаётся наружу | `PUBLIC_USER_SELECT` | — |

Активные брони — `pending` и `confirmed`: отменённые, завершённые и `no_show` не блокируют ни стол, ни пользователя. Исключающие ограничения в БД закрывают гонку двух одновременных запросов: второй получает ошибку, а сервис переводит её в понятный отказ.

### Матрица ролей в коде

[src/lib/permissions.ts](src/lib/permissions.ts) — единственный источник правды для серверных проверок; таблица в разделе 4 и тесты `tests/permissions.test.ts` должны с ней совпадать.

## 7a. Аутентификация и сессии (auth-lite)

- Регистрация: Zod-валидация, `bcryptjs.hash(password, 12)`, роль всегда `user`, запись `user_registered` в `AuditLog`, сессия открывается сразу.
- Вход: `bcryptjs.compare(inputPassword, user.passwordHash)`; на неверный пароль и неизвестный email — один ответ `401`; для неизвестного email сравнение идёт с фиктивным хешем, чтобы не выдавать наличие email временем ответа.
- Пароль: от 8 символов и не больше 72 байт (предел bcrypt).
- Сессия: случайный токен 256 бит в cookie `vm_session` (`HttpOnly`, `SameSite=Lax`, `Secure` включается переменной `SESSION_COOKIE_SECURE=true` для HTTPS, 7 дней); в таблице `Session` хранится только SHA-256 токена. Роль читается из БД на каждом запросе, поэтому смена роли действует сразу.
- Защита изменяющих запросов от CSRF: `SameSite=Lax` и проверка заголовка `Origin`.
- Ответы никогда не содержат `passwordHash` (единая выборка `PUBLIC_USER_SELECT`).

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `POST /api/auth/register` | все | регистрация и вход |
| `POST /api/auth/login` | все | вход |
| `POST /api/auth/logout` | все | выход |
| `GET /api/auth/me` | сессия | текущий пользователь |
| `GET /api/admin/users` | `user:list` (`admin`, `super_admin`) | список пользователей |
| `PATCH /api/admin/users/:id/role` | `user:change_role` (`super_admin`) | смена роли `user` ↔ `admin` |

Коды отказов: `401` нет сессии, `403` нет права или роль менять нельзя, `400` ошибка валидации, `409` дубль email или роль уже такая.

Клиент и сервер используют одни и те же `can` и `checkRoleChange` из `src/lib/permissions.ts`: интерфейс скрывает недоступные действия, решение всегда принимает сервер.

## 7b. Сценарий бронирования (API)

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `GET /api/availability?partySize=N` | все | доступные окна для N гостей; залогиненному не показываются окна, где у него уже есть активная бронь |
| `POST /api/bookings` | `booking:create` | создать бронь `{startsAt, partySize, comment?}`; стол назначает сервер |
| `GET /api/bookings` | `booking:view_own` | мои брони со столом, статусом, признаком и сроком самостоятельной отмены |
| `POST /api/bookings/:id/cancel` | `booking:cancel_own` | отменить свою бронь не позднее чем за 3 часа до начала |
| `GET /api/notifications` | `booking:view_own` | мои уведомления и число непрочитанных |
| `POST /api/notifications/read` | `booking:view_own` | отметить прочитанными все или одно (`{id}`) |

Страницы: `/book` (число гостей → дата → время → комментарий), `/bookings`, `/notifications`.

**Создание брони.** Сервер принимает только `startsAt`, `partySize` и `comment`. Поля `userId`, `tableId`, `status` отбрасываются: владелец берётся из сессии, стол подбирает `pickTable`, статус всегда `pending`. Окно должно совпасть с одним из окон по правилам (`candidateWindows`): прошлое время, время вне сетки, понедельник и дата дальше 14 дней дают `window_unavailable`. Затем проверяются закрытие окна администратором, конфликт с другой бронью пользователя и наличие свободного стола. Бронь, аудит `booking_created` и уведомление «Заявка принята» пишутся в одной транзакции.

**Гонки.** Если стол заняли между проверкой и записью, срабатывает ограничение БД `booking_table_no_overlap`: сервис подбирает другой стол (до 3 попыток), иначе отвечает `no_table`/`busy`. Нарушение `booking_user_no_overlap` превращается в `user_conflict`.

**Отмена.** Всегда по правилам владельца (дедлайн 3 часа), независимо от роли: отмена брони персоналом — отдельная операция администратора. Чужая бронь отвечает `404`, существование брони не раскрывается. После отмены пишутся аудит `booking_status_changed` и уведомление «Бронь отменена».

| Ответ | Когда |
|---|---|
| `400 validation_error` | неверный формат, число гостей вне 1–8 |
| `401` / `403` | нет сессии / нет права или чужой Origin |
| `409 window_unavailable` | время недоступно (прошло, вне правил, закрыто) |
| `409 user_conflict` | у пользователя уже есть активная бронь на это время |
| `409 no_table` / `busy` | нет свободного стола / стол не удалось занять |
| `403 deadline_passed` | до начала меньше 3 часов |
| `409 invalid_transition` | бронь уже отменена, завершена или `no_show` |
| `404 not_found` | брони нет или она чужая |

Одни и те же правила в трёх местах: число гостей (`MIN/MAX_PARTY_SIZE`) в форме, в Zod-схеме и в `CHECK` БД; окна и дедлайн — в `rules.ts`, которым пользуются и форма (через ответ сервера), и сервис; пересечения — в сервисе и в `EXCLUDE`-ограничениях БД.

## 7c. Административный контур

Доступен ролям `admin` и `super_admin`. Все страницы и API проверяют права на сервере; страницы защищены каждая отдельно (`requireStaffPage`), потому что layout при навигации не перерисовывается.

| Страница | Право | Что делает |
|---|---|---|
| `/admin` | `booking:view_all` | обзор: сколько заявок ждёт решения, сколько просрочено (время прошло, статус «Ожидает»), занятость сегодня и на 7 дней, очередь заявок с быстрым подтверждением и отменой, таблица «что доступно ролям» |
| `/admin/bookings` | `booking:view_all` | список броней: гость, назначенный стол, статус; фильтры по статусу и датам, быстрые фильтры («Ожидают решения», «Сегодня», «Ближайшие 7 дней», «Не пришли»); кнопки только допустимых переходов; история каждой брони |
| `/admin/slots` | `slot:manage` | расписание окон по правилам: загрузка зала (брони, свободные столы), закрытие и открытие окна с причиной |
| `/admin/history` | `audit:view_bookings` | кто, что и когда сделал; `admin` видит брони и окна, `super_admin` ещё роли и регистрации |
| `/admin/users` | `user:list` | список пользователей; кнопки смены роли только у `super_admin` |

| Метод и путь | Право | Назначение |
|---|---|---|
| `GET /api/admin/bookings?status=&from=&to=` | `booking:view_all` | список броней (даты по поясу ресторана, границы включительно, до 200 записей) |
| `POST /api/admin/bookings/:id/status` | `booking:change_status` | сменить статус `{status}` |
| `GET /api/admin/slots` | `slot:manage` | расписание окон с загрузкой |
| `PUT /api/admin/slots` | `slot:manage` | закрыть или открыть окно `{startsAt, closed, reason?}` |
| `GET /api/admin/audit?entityType=&entityId=&limit=` | `audit:view_bookings` | история; набор сущностей зависит от роли |

**Смена статуса.** Допустимые переходы — машина состояний из раздела 6. Из `cancelled`, `completed` и `no_show` возврата в активные статусы нет ни у `admin`, ни у `super_admin`: попытка даёт `409 invalid_transition`, ничего не записывается. Сотрудник отменяет бронь и после дедлайна гостя. Статус меняется условным обновлением (`WHERE status = прежний`), поэтому из двух одновременных решений срабатывает одно. Каждая смена пишет `booking_status_changed` с автором, прежним и новым статусом и отправляет гостю уведомление.

**Окна.** Закрыть можно только окно из расписания по правилам. Закрытое окно не показывается гостям и не принимает брони; уже созданные брони не отменяются, а ответ сообщает их число, чтобы администратор обработал их вручную. Повторная установка того же состояния даёт `409 no_change` и не засоряет историю. Закрытие и открытие пишут `slot_closed`/`slot_reopened`.

**История.** Каждая запись содержит автора (имя и роль), время, понятное действие и объект: создание, подтверждение, отмена (рестораном или гостем), завершение, «не пришёл», смена роли, закрытие окна. Запрос чужого типа сущности возвращает пустой список, а не ошибку и не данные.

**Что видно по ролям.** Страница `/admin` показывает таблицу возможностей `admin` и `super_admin`, построенную из той же матрицы `CAPABILITIES`/`PERMISSION_MATRIX`, что проверяет сервер; страницы пользователей и истории прямо говорят, что недоступно `admin`.

**Открытое решение.** Статусы `completed` и `no_show` можно поставить и до начала брони: машина состояний этого не запрещает. Если нужно разрешать только после начала, это одно правило в `checkTransition`.

## 8. Визуальное направление
